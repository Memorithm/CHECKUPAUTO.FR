# Notification delivery policy

## Rule

Mercure is a data source only. CyberCheck must not call Mercure endpoints that send customer reminders or review-request emails.

The delivery path is intentionally separated:

`Mercure data -> CyberCheck decision engine -> NotificationBroker -> Checkup Auto transport -> customer`

The former Mercure Google-review sender is explicitly disabled in `mercure_admin_client.py`.

## NotificationBroker

`notification_broker.py` is the delivery boundary. It creates a deterministic idempotency key from channel, category, business reference and recipient, records delivery state without persisting the raw recipient or message body, leases in-flight deliveries to prevent concurrent duplicate sends, and permits retries after failures. The administration API exposes read-only status at `/api/admin/notifications/status`.

The broker supports e-mail and APNs. APNs remains non-delivering until Apple credentials are present and `CYBERCHECK_MOBILE_PUSH_ENABLED` is explicitly enabled; this activation gate prevents central push delivery from duplicating the application's local fallback reminders during rollout.

## Email transports

`email_gateway.py` supports two Checkup Auto-owned transports. `auto` mode preserves the SMTP relay when configured and otherwise uses the Gmail API when the Google IntegrationHub has the `gmail.send` scope and a validated sender address.

Runtime selector:

- `CYBERCHECK_EMAIL_TRANSPORT`: `auto` (default), `smtp` or `gmail`.

SMTP variables:

- `CYBERCHECK_SMTP_FROM`: sender address; enables SMTP;
- `CYBERCHECK_SMTP_HOST`: optional, defaults to `127.0.0.1`;
- `CYBERCHECK_SMTP_PORT`: optional, defaults to 25 for local plain relay;
- `CYBERCHECK_SMTP_MODE`: `plain`, `starttls` or `ssl`;
- `CYBERCHECK_SMTP_USERNAME` and `CYBERCHECK_SMTP_PASSWORD`: optional authenticated relay credentials. They must be configured together and authentication is refused over `plain` mode, so credentials cannot be sent without TLS.

Gmail variables/settings:

- connect the Gmail service from IntegrationHub with `https://www.googleapis.com/auth/gmail.send`;
- configure `Gmail · Adresse d’envoi` in the private Google settings;
- `CYBERCHECK_GMAIL_FROM` is an optional runtime fallback for that sender setting.

OAuth client secrets and refresh tokens remain under `/root/CyberCheckPrivate/integrations` with private filesystem permissions. No OAuth token is written into the notification ledger.

## Operational transport preflight

The administration console exposes an explicit **Tester les transports** action backed by `/api/admin/notifications/preflight`. The check never sends a customer e-mail or an APNs notification. It returns normalized readiness states only and never returns passwords, OAuth tokens, APNs device tokens or the APNs private key.

- SMTP opens the configured connection, negotiates TLS when requested, authenticates when runtime credentials are configured, executes `NOOP`, then closes the session.
- Gmail validates the configured sender and `gmail.send` grant, then deliberately forces an OAuth refresh against Google's token endpoint. This verifies the current refresh grant/client credentials without creating a Gmail message.
- APNs validates Key ID, Team ID and topic locally, parses the private `.p8` key as EC P-256, and proves that an ES256 provider JWT can be generated. It does not contact APNs and does not require a device token.

The preflight is manual rather than tied to every status refresh so provider connections are not generated by routine administration polling.

## Mercure customer fields

The e-mail address used for reminders and review follow-up comes from the verified Mercure calendar `extendedProps.email` field. It is read only at delivery time and is not copied into the durable reminder inventory or NotificationBroker ledger.

## Google review follow-up

`CYBERCHECK_GOOGLE_REVIEW_URL` must be a validated HTTPS Google review URL. The follow-up engine sends the request through `notification_broker.py`, which delegates to `email_gateway.py`. It stores the Mercure appointment identifier and delivery state, but not the customer's e-mail address or message body.

## CT due-date reminder pipeline

CyberCheck reads the verified Mercure calendar schema and resolves `vehiculeId` to `/admin/get-vehicule/<id>`, where `date_echeance` is the control due-date source. The local reminder inventory stores only provider technical identifiers, due date and last source appointment. Customer e-mail addresses are resolved from Mercure only at delivery time and are never persisted in the reminder inventory.

The dispatch policy is shared with the iOS core: J-60, J-30, J-15, J-7 and J-1 at 09:00 Europe/Paris. Delivery is routed exclusively through NotificationBroker. Its idempotency reference hashes the provider vehicle identifier before persistence.

A recent Mercure window is refreshed on every cycle. Historical coverage is progressively backfilled in bounded 31-day chunks up to 730 days so the integration does not issue an unbounded burst of provider requests. Missing e-mail transport configuration prevents delivery but does not prevent due-date synchronization.

## Mobile bootstrap policy

The public endpoint `/api/mobile/bootstrap` exposes only non-secret mobile policy: reminder lead days, delivery hour and timezone, the public booking URL, the configured referral reward amount, application landing/download state, and whether central push is actually active. It does not expose Mercure identifiers, customer data, OAuth material, APNs credentials or administration configuration.

The iOS application validates schema version 1 and the reminder policy before applying it. If the endpoint is unavailable or invalid, the app keeps the baked-in safe defaults (J-60/J-30/J-15/J-7/J-1 at 09:00 Europe/Paris and the public Mercure booking URL). Local notifications remain the safe fallback until both the server declares central push active and that specific installation has successfully registered its APNs token.

## Mobile due-date push pipeline

The authenticated endpoint `/api/mobile/reminders/sync` receives a full snapshot of at most 24 mobile deadlines for an installation. Each entry contains only an opaque UUID and an ISO due date; registration plates, vehicle labels, Mercure identifiers and customer data never enter this registry. Device unregister and APNs-token reassignment purge stale mobile deadlines.

`mobile_reminder_dispatch.py` evaluates those dates with the same J-60/J-30/J-15/J-7/J-1 policy and routes eligible notifications through `NotificationBroker`. The APNs environment is selected per registered device (`sandbox` or `production`) rather than globally, so Debug and Release installations can coexist safely.

## Delivery failure semantics

E-mail failures are typed before they reach `NotificationBroker` so the broker can apply the same resilience policy used by APNs without parsing human-readable exception text.

- Gmail HTTP `429` and `5xx` responses are transient. `Retry-After` is preserved when Google provides it and otherwise the broker applies bounded exponential backoff with jitter.
- Gmail OAuth/authorization failures are configuration errors and open the transport circuit instead of being retried as if they were network outages.
- Gmail non-retryable request failures are recorded as permanent delivery failures.
- SMTP `4xx` replies are transient. Recipient `5xx` replies are permanent. Authentication and sender-configuration failures are configuration errors.
- Permanent failures are retained in the idempotent ledger and the same business delivery is suppressed on later dispatch cycles instead of being sent repeatedly.

The broker persists only the normalized failure class and a redacted diagnostic; raw recipients, message bodies, OAuth tokens and APNs tokens are not written to the notification ledger.

## Mobile deadline source precedence

The private mobile deadline registry records deadline provenance. device is the local/mobile fallback source; mercure is the authoritative server source. If any authoritative Mercure deadline exists for a registered installation, remote mobile dispatch selects only Mercure deadlines for that installation. Device-submitted rows remain dormant as a fallback and become eligible again only if the authoritative snapshot is explicitly removed.

The public /api/mobile/reminders/sync path is restricted to device rows and cannot overwrite an authoritative row. sync_authoritative_deadlines() is internal-only and is not wired to a public HTTP route. Verified installation-to-Mercure vehicle bindings are created by one-time claims. The authenticated post-inspection QR channel can populate them once the Apple Application Identifier Prefix and signed Associated Domains capability are configured.

## Secure mobile vehicle binding

Vehicle-to-installation binding uses a one-time high-entropy claim. The raw claim token is returned only to the trusted internal issuer and is stored only as a SHA-256 digest while pending. Claims expire, are deleted on successful consumption and cannot be replayed.

The public surface exposes only POST /api/mobile/claims/consume. There is deliberately no HTTP route for claim issuance. A successful consume returns an opaque binding UUID and never returns the Mercure vehicle or customer identifiers. The internal mobile_authoritative_sync worker maps active bindings to the already-synchronized reminder inventory and feeds authoritative dates into the private mobile deadline registry.

Customer claim delivery is implemented as an authenticated admin-only post-inspection QR flow. The admin request supplies only a vehicle identifier; the server resolves client identifiers from its authoritative Mercure reminder inventory before invoking the internal issuer. QR SVG generation is local, the raw token is never persisted, and issuance is refused until the Apple association identity is configured.

## Installation identity versus APNs channel

Mobile installation identity is registered independently from notification permission. /api/mobile/installations/register stores the installation UUID and a hash of its registration secret without requiring an APNs token. This allows a valid vehicle claim to be consumed before notification permission is granted.

/api/mobile/devices/unregister disables only the APNs channel and removes remote-dispatch deadlines; it intentionally preserves the verified vehicle binding. /api/mobile/installations/delete is the authenticated destructive operation that removes the installation and its bindings. This separation prevents a temporary notification opt-out from silently unlinking the customer's vehicle.

## iOS Universal Link claim client

The iOS core can validate and consume a vehicle claim without activating a claim-delivery channel. The accepted canonical form is an HTTPS CheckupAuto URL at /app/claim with the claim token in the URL fragment rather than the query string. HTTP, foreign hosts and query-carried tokens are rejected.

The app ensures its installation identity is registered before posting the opaque token to /api/mobile/claims/consume and accepts only an opaque binding UUID in the response. The app entitlement now includes only `applinks:www.checkupauto.fr`; the server AASA document authorizes only `/app/claim`. AASA publication and customer QR issuance remain fail-closed until a valid Apple Application Identifier Prefix is present. No custom URL scheme is enabled.

## Durable iOS privacy purge

Full installation deletion is server-confirmed before local destruction. After the server removes the installation and its vehicle bindings, the app deletes both Keychain identity records, clears locally stored vehicle deadlines and removes scheduled local reminders.

A local suppression tombstone prevents automatic installation recreation on later launches or foreground transitions, even when iOS notification permission remains granted. Reactivation requires an explicit user action such as enabling CheckupAuto again or consuming a new valid vehicle claim.

If server deletion fails, local identity and vehicle data are retained so the operation can be retried. Mercure regulatory records are outside this mobile purge and are not modified.
